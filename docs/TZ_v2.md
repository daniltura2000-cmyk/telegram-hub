> Дата: 05.11.2026 · Статус проєкту: v1.x працює (77 тестів, живий бот @try32323_bot)
> Основа: повний аудит коду (архітектурна інвентаризація, gap-аналіз, реєстр ризиків, бенчмарки у tests/perf_notes.md)

## 1. Призначення і межі системи

**TelegramHub** — самохостинговий комплекс із двох частин:

1. **Контрольний бот** (Bot API, aiogram 3) — панель керування для адміністратора: API-ключі LLM, підключення власного Telegram-акаунта, промпти, база знань, аналіз стилю, налаштування авто-відповідей, журнал Q&A, нагадування, профілі.
2. **Юзербот** (MTProto, Telethon) — входить в акаунт власника і відповідає на вхідні повідомлення від його імені через LLM, імітуючи його стиль письма.

**Поза межами (non-goals):** масові розсилки, спам, робота з чужими акаунтами, multi-tenant SaaS.

**Поточний стек:** Python 3.14, aiogram 3.24, Telethon 1.41, httpx (без LLM-SDK), SQLite (stdlib, через asyncio.to_thread), segno (QR), pytest. Все в одному asyncio-процесі.

## 2. Стан на сьогодні (зафіксуйте як базу)

Що вже працює і покрито тестами:

| Блок | Реалізація |
|---|---|
| LLM-шар | 3 провайдери (OpenAI-сумісний / Anthropic / Gemini), httpx, ретраї з бекофоном, Retry-After, probe ключа + верифікація моделі живим викликом (429 = попередження, 403/404 = відмова) |
| Підключення акаунта | код + QR-логін (без SMS), обробка ApiIdInvalid/FloodWait, 2FA |
| Burst-двигун | черга на чат, дебаунс 2 с, детект друку (UserUpdate), поріг «3 повідомлення → відповідай», медіа-плейсхолдери (стікер/фото/голосове), «людське» надсилання (випадкова затримка, typing, 2–3 частини) |
| Контекст | останні N повідомлень з мітками «Я:»/«Співрозмовник:» і часом [HH:MM] + «Зараз» |
| Анти-ШІ | strip_ai_tells (ем-дефіси, канцелярит, assistant-стартери) + правила в промпті |
| Персона | аналіз стилю (1/кілька/всі чати), граматичний рід у профілі, базовий промпт + База знань (до 15 000 символів, експорт .md) |
| Довідка | журнал Q&A (авто, 2000 символів/запис), нагадування (відносний і абсолютний час), профілі-сніпшоти налаштувань+промпту+БЗ |
| Інфра | лог-ротація, graceful shutdown, git, CI (3.12+3.13), README з ToS-попередженням |

Відомі технічні борги (з аудиту, з посиланнями):

- `get_settings()` читається на **кожне** вхідне повідомлення + щоразу відкриває 2 sqlite-з'єднання (db.py:294–296, userbot.py:247) — ~1.1 мс/читання, ×N на burst.
- З'єднання-per-виклик у всьому db.py (db.py:142–146); немає WAL.
- FSM — MemoryStorage: перезапуск процесу ламає незавершені діалоги (main.py:59).
- `close_pending()` — мертвий код, ніде не викликається (control_bot.py:1588).
- Аналіз стилю виконується inline у хендлері — блокує меню до хвилини, можна запустити двічі паралельно (control_bot.py:786–848).
- Немає FloodWait/reconnect у userbot (userbot.py: без обробки), клієнт «мовчки помирає» — connected лишається True (userbot.py:231–233).
- Секрети у plaintext у SQLite: api_key (db.py:26), api_hash (db.py:64), приватні листування в qa_journal (db.py:68–76).
- Секрети вводяться в чат бота і залишаються в історії Telegram (control_bot.py:344, 545, 626).
- Google-ключ у query-параметрі URL (google_provider.py:14) — витікає у логи проксі.
- OpenAI/Gemini payload без max_tokens (openai_compat.py:17, google_provider.py:21–30) — необмежена довжина і вартість відповіді.
- Немає лічильника токенів/витрат, usage з відповідей викидається.
- Пороги двигуна (DEBOUNCE/TYPING_GRACE/MAX_WAIT/THRESHOLD) hardcoded — не керуються з меню (userbot.py:53–62).

## 3. Цілі версії 2.0

1. **Безпека**: секрети не читаються з диска і не світяться в чатах більше ніж потрібно.
2. **Надійність**: юзербот живе тижнями без нагляду; падіння = відновлення + алерт, а не тиша.
3. **Якість «людини»**: контекст-пам'ять, пер-чат персона, стохастика поведінки.
4. **Керованість витрат**: ліміти токенів, лічильник, fallback між ключами.
5. **Власний код можна тестувати** на рівні FSM і двигуна без мережі.

## 5. Фаза B — Надійність (3–5 днів)

### B1. Стійкість юзербота
- Цикл нагляду (watchdog, задача в main.py): кожні 60 с `client.is_user_authorized()` + ping-запит; при обриві — reconnect з експоненційною затримкою (1→2→4…хв, max 30 хв), алерт адміну при 3 невдачах підряд.
- Обробка FloodWaitError у send_message/iter_messages: спати рівно seconds, відповідь відкладається (не втрачається — burst повертається в чергу).
- Send-retry: 1 повтор send_message при TransportError.

### B2. Персистентний стан підключення
- ConnectStates/QrStates у SQLiteStorage (aiogram) або власна таблиця fsm_state(user_id, state, data json).
- _pending_clients рестарту-стійкі: після рестарту процесу меню «Підключити акаунт» показує «продовжити з кроку N».
- Закликати close_pending() у shutdown (main.py).

### B3. Розщеплення процесів (опційно, рекомендовано при >1 акаунта)
- userbot-воркер як окремий процес/задача з двонаправленою чергою (asyncio.Queue або Redis) до control-бота.
- Контракт повідомлень: {type: incoming|reply_sent|error, chat_id, ...}.

### B4. Спостережуваність
- «📊 Статус» доповнюється: uptime процесу, стан Telethon (підключений/нема), кількість відповідей за добу, останні 5 помилок (не одна).
- Структурований лог-рядок на кожну відповідь: chat, burst_size, latency_llm_ms, tokens, fallback_used.

## 6. Фаза C — Безпека (3–4 дні)

### C1. Секрети на диску
- App-level шифрування: master key з env (SECRET_MASTER_KEY) або Windows Credential Manager; AES-GCM (cryptography) для llm_keys.api_key, accounts.api_hash.
- Міграція: при старті — якщо колонки зашифровані префіксом `enc:`, розшифрувати в пам'ять; нові записи — тільки шифровані. Зворотна сумісність читання.
- Сесійні файли: права доступу (Windows ACL), контроль целосності (hash у БД).

### C2. Секрети в чаті
- Введення api_hash/2FA/api_key через **edit-time видалення**: після кроку FSM бот редагує/видаляє повідомлення користувача з ключем (бот має права видалення в приватному чаті з Bot API — message.delete()).
- Альтернатива для API-ключів: inline-mode або /delete одразу після читання. Плюс попередження «повідомлення з ключем буде видалено».
- Gemini-ключ: переносити з URL у header x-goog-api-key (google_provider.py:14).

### C3. Мульти-адмін семантика
- Визначити: 1 акаунт = 1 «власник» (перший адмін, що підключився); інші адміни бачать статус read-only і не можуть міняти налаштування, якщо не власники.
- Прибрати get_any_account-подібні «першим рядком» фолбеки з запису (db.py:420–426).

## 7. Фаза D — Якість «людини» (4–6 днів)

### D1. Пам'ять розмов (memory)
- Після кожної відповіді: коротке резюме діалогу (LLM, 1–2 речення) → таблиця chat_memory(chat_id, summary, updated_at), оновлення раз на K повідомлень.
- В system prompt: «Пам'ять про цю людину: {summary}». Довгострокова зв'язність: бот пам'ятає, про що говорили вчора, без 50-повідомлень контексту.
- Кнопка «🧹 Забути цей чат» (видалення пам'яті) + перегляд пам'яті в журналі чата.

### D2. Пер-чат персона
- settings_per_chat(chat_id, prompt_override, style_note, enabled) — таблиця; редактор у журналі чата («Налаштувати відповіді тут»).
- Приклади: «тут писати коротко», «тут не жартувати», «тут завжди відповідати питанням».

### D3. Стохастика поведінки (людяність 2.0)
- Розподіл затримки не uniform, а log-normal; іноді (10%) «відповісти швидко» (0.5–1 с), іноді (5%) «затриматись» (20–40 с) — «зайнятий».
- Іноді (15%) відповісти без typing-індикатора (відповів «після паузи»); іноді дві частини з довшою паузою.
- Реакції на медіа: на стікер — іноді просто емодзі-відповідь без тексту.
- Всі ймовірності — константи в конфігу, не в меню (щоб не перевантажувати UI).

### D4. Еволюція стилю
- Періодична (раз на тиждень або на кнопку) ре-аналізація: беремо останні відповіді бота + власні повідомлення з журналу, порівнюємо з профілем, оновлюємо. Кнопка «🔄 Оновити профіль з останніх розмов».

## 8. Фаза E — LLM-шар промислового рівня (3–4 дні)

1. **Токен-ліміт контексту**: оцінка ~4 символи/токен; обрізання context_messages так, щоб system+context+burst ≤ budget (налаштовуваний, дефолт 6000 токенів).
2. **Rate limiter per provider**: токен-бакет (наприклад Gemini free: ~15 req/хв) — черга на провайдера, охолодження при 429 бекофом уже є, ліміт не дає його досягти.
3. **Streaming не потрібен** (відповідь відправляється «людськи» з паузами — streaming нічого не дає). Зафіксувати як рішення.
4. **Кеш ідентичних запитів**: 5-хвилинний LRU (system+user hash) — захист від подвійного дзвінка при гонці burst.
5. **Провайдер-agnostичні моделі в UI**: показувати «провідник» моделей із коротким описом при виборі (контекст з probe).

## 9. Фаза F — UX і доставка (2–3 дні)

1. **Onboarding**: перший /start → покроковий чекліст (ключ → акаунт → стиль → вайтлист → увімкнути) з прогресом («Крок 2 з 5»).
2. **Мова інтерфейсу**: UA/EN перемикач (texts.py → словник за ключем, мова в settings).
3. **Імпорт/експорт конфігурації**: JSON-файл усього налаштування (профілі, промпт, БЗ) — для бекапу і переносу. БЗ вже експортується — узяти той механізм.
4. **Docker-деплой**: Dockerfile (python:3.12-slim, volume /data /sessions /logs), docker-compose, інструкція для Windows (Task Scheduler) і Linux (systemd unit у README).
5. **Версія і health**: /version команда; лог «startup OK v2.0».

## 10. Фаза G — Тестованість і CI (постійно)

Необхідні шви (seams):
- **Clock** (интерфейс now()) — підмінюється в тестах (reminders, debounce, cooldown).
- **BotAPIPort** (send_message/edit/delete для контрол-бота) — fake у тестах FSM.
- **TelethonPort** (get_chat/get_messages/send_message/typing) — fake у тестах двигуна; прибрати прямий import Telethon із control_bot.py (наслідувати через userbot).
- Винос хендлерів із замикань у методи/функції з явними залежностями — уможливлює юніт-тести FSM-переходів.
- E2E-тест двигуна: fake-повідомлення → burst → одна відповідь (уже є в bench_engine — розвинути до assertion-набору).

CI: + python 3.14 у матрицю; крок «pytest -q --maxfail=1».

## 13. Критерії приймання v2.0 (вимірювані)

1. Burst-10: ≤2 читання settings, ≤1 get_chat (бенчмарк у CI).
2. Вбивство активного LLM-ключа посеред розмови → відповідь іде через fallback, адмін отримує 1 нотис (A7).
3. `grep` по hub.db не знаходить plaintext api_key/api_hash (C1).
4. Після kill -9 процесу і рестарту: діалог підключення пропонує продовжити; burst-черга втрачає максимум невідправлені повідомлення, не зависає (B2).
5. Симуляція обриву мережі на 5 хв → авто-reconnect, алерт, продовження відповідей (B1).
6. Витрати за тиждень видно в боте, вартість/добу обмежена лімітом (A6/E1).
7. Пам'ять чата: після 50 повідомлень бот коректно згадує факт з першої десятки (D1, ручна перевірка).
8. Усі вихідні тексти без «—», «Сподіваюсь», «Резюмуючи» (автотест на strip_ai_tells уже є).
